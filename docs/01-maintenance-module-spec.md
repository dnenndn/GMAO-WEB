# Maintenance / Work Order Module — Functional Spec (Phase 1)

Reverse-engineered from the legacy GMAO WinForms app (`ot_*.cs`, `ordre_travail.cs`,
`Demande_Intervention.cs`, `lancement_ot_preventive.cs`, `preventive_*.cs`).

## 1. Core concepts

| Legacy term | Meaning | Web entity |
|---|---|---|
| DI (`demande_intervention`) | Intervention Request — anyone reports a problem | `DemandeIntervention` |
| OT (`ordre_travail`) | Work Order — the actual maintenance job, created from a DI or generated by a preventive plan | `OrdreTravail` |
| Gamme opératoire | A reusable operating procedure/checklist (used for preventive OTs) | `GammeOperatoire` |
| Intervenant | A technician/staff member | `Intervenant` |
| Centre de charge | Cost/work center | `OtCentreCharge` |

## 2. Work order types

- `Corrective` — reactive repair from a breakdown/anomaly
  - Sub-types: `Corrective Curative`, `Corrective Palliative`
- `Préventive Systématique` — scheduled by calendar interval
- `Préventive Syst Compteur` — scheduled by equipment counter/meter reading (e.g. every 500 operating hours)
- `Préventive Conditionnelle` — triggered by a measured threshold being crossed
- `Travaux Neufs` — new works / installation projects

## 3. Work order statuses (lifecycle)

```
En Préparation → Planifié → En Cours → Clôturé
                     ↓
       En Attente Arrêt Machine / Sous-Traitant à contacter
```
Urgency levels: `Elevée` (High) / `Moyenne` (Medium) / `Faible` (Low) — same 3 levels used on both the DI and the OT.

## 4. End-to-end flow

1. **Intervention Request (DI)** is raised by any user: describes the problem
   (`description_defaillance`), which equipment/sub-equipment/organ is affected,
   urgency, and whether it requires a machine stoppage (`arret_machine`).
2. A supervisor **confirms, refuses, or reschedules** the DI (`da_confirmer`,
   `da_refuser`, `da_reporter` pattern reused across the app for approvals).
3. Confirming a DI **creates a Work Order (OT)**, copying over equipment,
   urgency, and defect/anomaly reference, and generating a sequential `n_ot`
   number.
4. **Preventive OTs bypass the DI step** — they're auto-generated by the
   scheduler (`lancement_ot_preventive.cs`) based on:
   - Systematic plans (fixed calendar interval)
   - Counter-based plans (equipment meter reaches a threshold)
   - Conditional plans (a measured value crosses a threshold)
5. The OT is **planned**: assign supervisor (`id_superviseur`), classify
   (`id_classe`), and schedule staff against **resource/function slots**
   (`ot_ressources_fonction` → `ot_ordo_intervenant` for who + when,
   `ot_ordo_intervention` for what operation — repair/test/diagnostic).
6. Execution: actual start/end (`date_debut`/`heure_debut`, `date_fin`/`heure_fin`)
   are recorded distinct from the planned window (`debut_prevu`/`fin_prevu`) —
   this is what powers on-time/delay reporting later.
7. **Parts consumption** is tracked via `bsm`/`bsm_article` (stock issue
   linked to the OT) — this ties the maintenance module to Inventory (Phase 2).
8. **Diagnostics** (root-cause analysis) can be attached: Ishikawa
   fishbone-style symptom tracking (`ot_diagnostic_m`, `symptome`) and AMDEC.
9. Closing the OT (`statut = 'Clôturé'`) locks the actual-vs-planned times and
   feeds the KPI/Pareto reporting screens (cost & reliability, by equipment /
   family / cause / technician).

## 6. Notable business rules found in the code

- An OT's `n_ot` is a generated sequential/human-readable reference — needs a
  numbering scheme decision (e.g. `OT-2026-000123`) since the legacy format
  wasn't fully recoverable from static analysis alone.
- Actual duration is computed as `DATEDIFF(HH, debut, fin)` — hour-granularity,
  not minutes.
- Equipment is a **self-referencing tree** (`atelier` → `equipement` →
  `sous_equipement` → `organe`), and an OT stores references to all 4 levels
  independently rather than just the leaf node — worth deciding whether to
  keep this denormalized shape or derive it from a single equipment path in
  the web version (recommend: keep for now, to preserve reporting behavior).
- Soft-deletes are used everywhere (`deleted` boolean columns) rather than
  hard deletes — carried over into the Prisma schema.
